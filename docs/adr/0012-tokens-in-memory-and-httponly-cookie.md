# Токены: access в памяти, refresh в HttpOnly-cookie

Статус: принято
Дата: 2026-11-15

Access-токен (15 минут) клиент держит **только в памяти** (`AccessTokenStore`) и отправляет в заголовке `Authorization: Bearer`. Refresh-токен (1 день) лежит в cookie `HttpOnly`, `SameSite=Strict`, `Secure` вне локальной разработки, с `Path=/rest/auth`: браузер шлёт её только на `/auth/*`. Эта cookie открывает ровно два маршрута: `POST /auth/refresh` (новый access-токен и пользователь) и `POST /auth/sign-out` (отзыв). Все остальные маршруты принимают только Bearer-токен. При старте приложение само запрашивает `/auth/refresh` (app initializer), так что перезагрузка страницы сессию не теряет. Истёкший access-токен (401) клиент один раз обновляет через `/auth/refresh` и повторяет запрос; параллельные запросы делят одно обновление.

**Почему.** `localStorage` и `sessionStorage` доступны любому скрипту страницы: одна XSS отдаёт токен целиком (OWASP: не хранить токены сессии в Web Storage). HttpOnly-cookie скрипту недоступна. Но cookie, которую браузер сам добавляет к любому запросу, открывает путь для CSRF, поэтому она не служит сессией для API: её принимает только `/auth/refresh` и `/auth/sign-out`, а действия выполняются с Bearer-токеном, которого у чужого сайта нет. `SameSite=Strict` и CORS с белым списком origin закрывают остальное.

## Рассмотрено

- **Всё в `localStorage` (было).** Просто, но уязвимо к XSS. Отклонено.
- **Только cookie как сессия на всех маршрутах (BFF, серверная сессия).** Самый надёжный вариант для монолита на одном origin (целевая схема, [ADR 0001](0001-monolith-nest-angular-ssr-on-vps.md)), но требует CSRF-токенов на каждую записывающую операцию и хранилища сессий. Возвращаемся к нему, когда приложение переедет на один origin с SSR.
- **Refresh-токен без ротации.** Кража cookie давала бы доступ на сутки, пока владелец не выйдет. Отклонено: ротация сделана (см. ниже).
- **Access-токен в cookie `HttpOnly`.** Убирает JS-доступ, но возвращает CSRF на все маршруты. Отклонено.

## Ротация и отзыв

Каждый вход создаёт сессию (`sessions`, одна на устройство). Refresh-токен несёт `sid` (сессия) и `jti` (номер токена в ней); каждое обновление выдаёт новый токен, а прежний перестаёт быть действительным. Если прежний токен предъявлен снова, это копия: вся сессия удаляется, для вора и для владельца (владелец входит заново). Исключение на 10 секунд: две вкладки могут обновиться одновременно, второй запрос получает access-токен без новой cookie (браузер уже держит новую). Выход удаляет сессию только этого устройства; смена пароля (`tokenVersion`) отзывает сессии всех устройств. Запись сессии удаляет сама MongoDB по TTL-индексу, когда истёк последний токен. Сессия скользящая: активный пользователь остаётся (токен живёт сутки с последнего обновления).

## Последствия

Перезагрузка страницы стоит одного запроса `/auth/refresh` до первого экрана. Вкладки одного браузера синхронизируются через `BroadcastChannel`: выход в одной завершает остальные, вход в одной подхватывают остальные из cookie. Для разных origin клиента и API нужен CORS с `credentials` и точным списком origin (уже есть). Подробности и тесты: [S8.12](../backlog/E08-security-privacy/S8.12.md).
