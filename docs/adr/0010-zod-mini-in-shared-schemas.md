# Схемы API на zod, в общем пакете `zod/mini`

Статус: принято
Дата: 2026-11-13

Валидация переехала с valibot 0.29 на zod 4 ([S1.12](../backlog/E01-dependency-upgrades/S1.12.md)). Схемы формы данных объявлены один раз в `packages/schemas` и написаны на **`zod/mini`**: клиент и сервер проверяют ими одно и то же, типы выводятся через `z.infer`. Серверные DTO, которых нет у клиента (обновление игрока, создание игроков, пароль), остаются на классическом `zod` ради удобного API: размер серверного кода не важен.

Причина выбора `zod/mini` — размер клиентского бандла. Измерено: те же схемы на классическом `zod` добавляют к клиенту около 91 кБ gzip (классический API не режется tree-shaking'ом), на `zod/mini` около 7 кБ. В реальной сборке клиента суммарный JS стал меньше на 391 кБ (2368 → 1977 кБ), первичная загрузка 305 кБ gzip.

## Рассмотрено

- **Классический `zod` везде.** Удобнее (цепочки `.trim().min(3)`, `.array()`), но +91 кБ gzip на клиенте ради проверки, которой достаточно функционального API.
- **valibot 1.x.** Дёшев по размеру, но валидация проекта и так переписывалась с 0.29, а в пользу zod экосистема форм и `validateStandardSchema` ([ADR 0007](0007-signal-forms-single-store.md)).

## Последствия

В общем пакете схемы пишутся функционально: `z.object(...)`, `z.pipe(z.nullish(...), z.transform(...))`, `z._default(...)`, `.check(z.trim(), z.minLength(3))`, а не цепочками. Метода `.array()` у mini нет: списки объявлены как `gamesSchema`, `playersSchema`. Объявления схем, реэкспортируемые сервером, должны быть именно реэкспортами (`export { x as Y } from '@sfl/schemas'`): `const Y = x` даёт ошибку переносимости типов TS2883. Ответы API проверяются на клиенте в мягком режиме (ошибка пишется в консоль, данные проходят дальше, `STRICT` в `shared/api/checked-response.ts`): жёсткий режим включить после проверки на реальных данных.
