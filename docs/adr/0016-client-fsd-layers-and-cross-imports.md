# Клиент: слои FSD, публичный API слайсов и разрыв кросс-импортов

Статус: принято
Дата: 2026-11-16
Утверждено владельцем: 2026-11-16

Клиент рос с неполной раскладкой FSD: страницы и виджеты лежали внутри `entities`, сущности импортировали друг друга (`players` ↔ `games`, автокомплит игроков читал стор формы матча), у слайсов не было публичного API. Линтер границ ([S3.8](../backlog/E03-architecture/S3.8.md)) на такой структуре дал бы сотни ошибок.

## Решение

Следуем стандарту FSD v2.1 (skill `feature-sliced-design`), без исключений «для удобства».

1. **Слои:** `app` → `pages` → `features` → `entities` → `shared`. Слой `widgets` не используем (официально не рекомендован): блок экрана одной страницы лежит в `pages/<страница>/ui`, переиспользуемое действие — в `features`.
2. **Публичный API:** каждый слайс `entities`, `features`, `pages` отдаёт наружу только `index.ts`; импорт `@entities/player`, а не `@entities/player/model/...`. Правило проверяет ESLint (`no-restricted-imports` в `client/eslint.config.js`).
3. **Сегменты:** `ui/` (компоненты), `model/` (сторы, типы, правила), `api/` (запросы), `lib/` (утилиты слайса). Файлы названы по предметной области, а не по роли.
4. **Кросс-импорты сущностей.** Единственная связь: `game` хранит команды и игроков внутри матча, поэтому `entities/game` читает типы `entities/team` и `entities/player` через нотацию `@x` (`@entities/player/@x/game`, `@entities/team/@x/game`). Только типы, только для `game`. Объединять сущности не стали: у игрока и команды есть свои страницы и сторы. Обратных импортов нет.
5. **Кросс-импорты фич: стратегия C (сборка в верхнем слое).** Форма матча (`features/game-edit`) и автокомплит игроков (`features/player-select`) друг друга не знают. Автокомплит получает данные входами (`options`) и сообщает событиями (`picked`, `removed`, `createRequested`); форма даёт слот `<ng-content />`; страница `pages/game-edit` склеивает их адаптером `TeamPlayersAutocompleteComponent`.
6. **Именование слайсов.** `entities` — предмет в единственном числе (`game`, `player`, `team`, `captain`). `features` и `pages` — `<предмет>-<действие>`, чтобы слайсы одного предмета стояли рядом в списке папок. Фичи: `game-edit`, `game-delete`, `game-table`, `player-create`, `player-edit`, `player-delete`, `player-select`, `player-toggle-captain`, `captain-add`, `captain-select`, `captain-table`, `captain-toggle`, `auth-sign-in`. Страницы: `home`, `game-list`, `game-edit`, `game-details`, `player-list`, `player-details`, `captain-list`, `auth-sign-in`.
7. **Сборка:** маршруты собирает `app/app.routes.ts`, охранник маршрута — `app/admin.guard.ts`.

## Почему так

- Границы, которые проверяет линтер, не дрейфуют: новый кросс-импорт ломает `pnpm lint`.
- Автокомплит без стора проще тестировать и можно использовать вне формы матча.
- `@x` ограничен типами и одним потребителем; это прямое разрешение стандарта для случая, когда сущности нельзя слить.

## Рассмотрено

- **Слить `games`, `players`, `teams` в одну сущность.** Убирает `@x`, но смешивает три предметные области и их сторы.
- **Автокомплит как `shared/ui`.** Он не знает матчей, но знает игроков и их поля; в `shared` бизнес-термины не кладём.
- **Оставить `widgets`.** Граница с `features` размыта; блоки экрана одной страницы естественнее в `pages`.
