# Версия релиза: семвер в корневом package.json, release notes в Markdown

Статус: принято
Дата: 2026-11-18

Нужна версия, которая появится после выгрузки на VPS, поднимается в конце цикла фич и попадает в release notes ([S10.51](../backlog/E10-product-features/S10.51.md)). SFL — приложение, не библиотека: публиковать версию в npm не нужно, важно, чтобы одна версия описывала весь продукт.

**Решение.**

1. **Одна версия на продукт — поле `version` корневого `package.json`** (`"private": true` этому не мешает). У `client`, `server-nest`, `packages/*` стоит `0.0.0` и не меняется: это части одного продукта, не отдельные релизы.
2. **Семвер `MAJOR.MINOR.PATCH`**, значение для лиги:
   - `minor` — цикл с новыми возможностями для игроков или администраторов (обычный релиз);
   - `patch` — только исправления без новых возможностей;
   - `major` — несовместимое изменение, видимое людям: переезд данных, смена способа входа, смена правил расчёта в [GLOSSARY.md](../../GLOSSARY.md). Расхождение с CalVer из первой редакции S10.51 (`ГГГГ.ММ.N`): семвер показывает размер изменений, дату в релизе даёт отдельное поле.
3. **Первый релиз — `1.0.0`**, он выходит с выгрузкой на VPS. Истории до него на сайте — один блок «Early history» без версий, теги задним числом не ставятся; номера `0.x` в `client/package.json` и `server-nest/package.json` в релизы не переходят.
4. **Релиз делает владелец в конце цикла**, после `pnpm check`: `pnpm release <major|minor|patch>` поднимает версию, превращает черновик `docs/releases/NEXT.md` (заголовок и строки изменений пишутся по ходу цикла) в `docs/releases/X.Y.Z.md` с `version` и `date`, коммитит `chore(release): X.Y.Z`, ставит тег `vX.Y.Z`; пустой заголовок или список изменений — отказ. Без записи в `docs/releases/` релиза нет, без релиза закрытая история не считается выпущенной.
5. **Release notes — Markdown в репозитории** (`docs/releases/X.Y.Z.md`: дата, заголовок, изменения с видом и областью, ссылки на закрытые истории). База не нужна: версия, тег и заметки попадают в один коммит, нет расхождения между кодом и текстом, нет формы в админке. Страница и RSS строятся при сборке клиента; этапы до `1.0.0` лежат в `docs/releases/EARLY-HISTORY.md`.
6. **Версия в сборке.** Скрипт перед сборкой пишет `version`, короткий хеш коммита и дату в `client/src/environments/build-info.generated.ts` (не коммитится, как `api-url.generated.ts`). Сервер читает версию из корневого `package.json` и отдаёт её в публичном `GET /rest/version` (`APP_VERSION` из окружения важнее: в образе корневого `package.json` нет). Футер и страница релизов берут значения из сборки.
7. **Раздача.** Всё, что видит посетитель (версия, release notes, RSS), входит в статику клиентского бандла или в публичный `GET /rest/version`. Отдельно открывать ничего в Caddy не нужно: прокси раздаёт статику и проксирует `/rest/*`, как для остального сайта ([S7.3](../backlog/E07-vps-hosting/S7.3.md)).

## Рассмотрено

- **CalVer `ГГГГ.ММ.N`.** Не показывает размер изменений; «мажор» для сайта лиги не определён, а дата и так хранится в заметке.
- **Отдельные версии клиента и сервера.** Клиент и сервер выкладываются вместе, одна версия проще для футера и для вопроса «что сейчас на проде».
- **Release notes в MongoDB с вводом в админке.** Нужны схема, маршруты, права и миграции ради текста, который и так пишется в коммите; правка без деплоя лиге не нужна.
- **Автоматические инструменты (changesets, release-please).** Сделаны для публикации пакетов и PR-ботов; в проекте один владелец и один продукт, хватает короткого скрипта.
