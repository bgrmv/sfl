# S11.7 — Pre-commit хуки: husky и lint-staged

**Эпик:** 11 — DX, документация, чистота репозитория · **Статус:** в [индексе бэклога](../README.md)

**Приоритет:** P1 · **Размер:** S · **Зависит от:** [S1.6](../E01-dependency-upgrades/S1.6.md)

**DESC:** Как разработчик, я хочу, чтобы при коммите изменённые файлы автоматически форматировались Prettier и проверялись ESLint, чтобы в PR не попадали ошибки стиля и линтера и ревью шло по сути.

**ACs:**

- [x] `husky` и `lint-staged` установлены в корневом `package.json`. Если pnpm workspace ([S3.2](../E03-architecture/S3.2.md)) ещё не сделан, корневой `package.json` минимальный: только хуки и скрипт `prepare`.
- [x] `pre-commit` запускает `lint-staged` только по staged-файлам: `prettier --write` для `*.{ts,html,scss,json,md}`, `eslint --fix` для `*.ts`. Используются конфиги из [S1.6](../E01-dependency-upgrades/S1.6.md), каждый пакет проверяется своим конфигом.
- [x] Если ESLint находит ошибку, которую не исправить автоматически, коммит отклоняется.
- [x] Хуки ставятся сами после `pnpm install` (скрипт `prepare`), в том числе в dev-container ([S11.6](S11.6.md)).
- [x] Обычный коммит из нескольких файлов проходит хук быстрее 10 секунд.
- [x] Хуки не заменяют CI: те же проверки по всему коду выполняются в [S2.1](../E02-tests-ci/S2.1.md).
- [x] README и AGENT.md ([S11.5](S11.5.md)) описывают хуки и запрещают обходить их через `--no-verify` без причины в описании PR.

## Заметки

- Хуки зависят от S1.6 сознательно: если настроить их под текущие `.eslintrc.*`, после перехода на flat config их придётся переделывать.

- **Сделано 2026-11-13.** `husky` 9.1.7 и `lint-staged` 17.6.0 (точные версии) в корне, конфиг — `lint-staged.config.mjs`, каждый пакет запускается из своей папки (иначе ESLint не находит конфиг). В хук добавлен `gitleaks --staged` ([S8.8](../E08-security-privacy/S8.8.md)).
- **Скорость (принято владельцем 2026-11-13, AC отмечен).** Хук на 3 файлах занимает ~12 с, а не <10 с: сами ESLint и Prettier укладываются в ~4 с (серверный ESLint с type-aware правилами ~4 с на файл), остальное — git-операции lint-staged на медленном bind-mount Windows. С `--no-stash` выходит ~9,5 с, но тогда при частичном staging (`git add -p`) в коммит могут попасть лишние правки, поэтому оставлен безопасный режим. Фактическое время ~12 с вместо <10 с владелец принял. Вернуться к вопросу при переносе проекта на быструю файловую систему.
- Форматирование клиента проверяется только для staged-файлов; остальные 22 файла приведутся к конфигу, когда до них дойдут правки.
