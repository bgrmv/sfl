# S8.12 — Сессии и токены: отзыв, Secure, секреты JWT

**Эпик:** 8 — Безопасность и персональные данные · **Статус:** в [индексе бэклога](../README.md)

**Приоритет:** P2 · **Размер:** M · **Зависит от:** [S2.4](../E02-tests-ci/S2.4.md), [S8.9](S8.9.md)

**DESC:** Как владелец, я хочу, чтобы выход действительно завершал сессию, а токены были устойчивы к подделке и устареванию прав, чтобы украденная cookie или смена роли не оставляли доступа.

**ACs:**
- [ ] `sign-out` отзывает refresh-токен (список отозванных или версия токена в пользователе); после выхода `GET /auth/whoami` с прежней cookie отвечает 401 (G2). Тест в `test/api/`.
- [ ] Refresh-cookie выставляется с `Secure` вне локальной разработки (G3).
- [ ] При входе по refresh `req.user` и роли берутся из базы, а не из refresh-токена: смена роли действует сразу (G4). Тест после реализации ролей в [S8.9](S8.9.md).
- [ ] Секреты JWT проверяются при старте: минимум 32 символа, access и refresh различаются; приложение не стартует с коротким секретом. Убран `TODO: add secrets 100%` (G5).
- [ ] В токенах есть `iss` и `aud`, алгоритм зафиксирован при проверке (`verify` с `algorithms: ['HS512']`) (G5).
- [ ] В payload нет лишних персональных данных (достаточно `_id` и `roles`), клиент получает остальное через `GET /auth/whoami`; клиентская часть согласована с [S3.10](../E03-architecture/S3.10.md).

## Заметки

- Источник: [аудит безопасности 2026-11-13](../../audits/security-2026-11-13.md), находки G2–G5. Выход не отзывает сессию: подтверждено запросом (после `sign-out` `whoami` с той же cookie отвечает 200).
- Смена секрета JWT делает все выданные токены недействительными: выкатывать вне часов матчей.
