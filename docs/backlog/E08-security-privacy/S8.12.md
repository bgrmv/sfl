# S8.12 — Сессии и токены: отзыв, Secure, секреты JWT

**Эпик:** 8 — Безопасность и персональные данные · **Статус:** в [индексе бэклога](../README.md)

**Приоритет:** P2 · **Размер:** M · **Зависит от:** [S2.4](../E02-tests-ci/S2.4.md), [S8.9](S8.9.md)

**DESC:** Как владелец, я хочу, чтобы выход действительно завершал сессию, а токены были устойчивы к подделке и устареванию прав, чтобы украденная cookie или смена роли не оставляли доступа.

**ACs:**

- [x] `sign-out` отзывает refresh-токен (список отозванных или версия токена в пользователе); после выхода `GET /auth/whoami` с прежней cookie отвечает 401 (G2). Тест в `test/api/`.
- [x] Refresh-cookie выставляется с `Secure` вне локальной разработки (G3).
- [x] При входе по refresh `req.user` и роли берутся из базы, а не из refresh-токена: смена роли действует сразу (G4). Тест после реализации ролей в [S8.9](S8.9.md).
- [x] Секреты JWT проверяются при старте: минимум 32 символа, access и refresh различаются; приложение не стартует с коротким секретом. Убран `TODO: add secrets 100%` (G5).
- [x] В токенах есть `iss` и `aud`, алгоритм зафиксирован при проверке (`verify` с `algorithms: ['HS512']`) (G5).
- [x] В payload нет лишних персональных данных (достаточно `_id` и `roles`), клиент получает остальное через `GET /auth/whoami`; клиентская часть согласована с [S3.10](../E03-architecture/S3.10.md).

## Заметки

- Источник: [аудит безопасности 2026-11-13](../../audits/security-2026-11-13.md), находки G2–G5. Выход не отзывает сессию: подтверждено запросом (после `sign-out` `whoami` с той же cookie отвечает 200).
- Смена секрета JWT делает все выданные токены недействительными: выкатывать вне часов матчей.

- **На полях, 2026-11-15 (идея владельца, не в ACs).** Авто-рефреш access-токена на клиенте: функциональный интерсептор ловит `401` с кодом `TOKEN_EXPIRED`, один раз зовёт `/auth/refresh`, параллельные запросы ждут в очереди (`BehaviorSubject`) и повторяются с новым токеном; если рефреш не удался, `logout()` и пробросить исходный `HttpErrorResponse` дальше, чтобы `toResult()` увидел тело ошибки. Для этого в `API_ERROR_CODES` нужны `TOKEN_EXPIRED` и `REFRESH_TOKEN_EXPIRED`. Интерсептор не должен подменять тело ошибки, а запрос на `/auth/refresh` и `/auth/sign-in` не повторяется. Связано с [S3.10](../E03-architecture/S3.10.md) (общий перехватчик ошибок).

- **Сделано 2026-11-15.**
  - **Отзыв (G2).** У пользователя поле `tokenVersion`, токены несут `tv`. `sign-out` и смена пароля (`POST /users/:id/password`) увеличивают версию: все refresh-токены пользователя на всех устройствах перестают работать сразу. Access-токен без обращения к базе живёт до 15 минут: это сознательный компромисс статeless-проверки.
  - **Cookie (G3).** `Secure` везде, кроме `STAGE` `development` и `test`; те же флаги при очистке cookie.
  - **Роли из базы (G4).** Вход по refresh-cookie читает пользователя и роли из базы (`AuthService.refreshSession`), `whoami` тоже читает пользователя из базы.
  - **Секреты (G5).** `configuration.ts` не даёт стартовать с секретом короче 32 символов и с одинаковыми секретами; сообщение секрет не раскрывает. Dev-значения в `.devcontainer/server-nest.env` и локальный `server-nest/.env` обновлены (старые были короче 32 символов: у других разработчиков `.env` придётся обновить).
  - **`iss`, `aud`, алгоритм.** Issuer `sfl-api`, audience `sfl-access` и `sfl-refresh`: refresh-токен не проходит как access и наоборот; `verify` принимает только `HS512` (HS256 и `none` отклоняются).
  - **Payload** содержит `_id`, `roles`, `tv` (и стандартные `iat`, `exp`, `iss`, `aud`); остальное даёт `GET /auth/whoami`. Клиент токен не разбирает, поэтому клиентская часть не менялась.
  - Тесты: `test/api/sessions.test.ts` (17), `src/config/configuration.test.ts` (5), обновлены `access.test.ts` и `auth.guard.test.ts`.
- **При выкатке.** Все выданные до этого токены перестают быть действительными (новые `iss`/`aud`, `tv`): пользователям придётся войти заново. Делать вне часов матчей.
- **Хранение токенов и авто-рефреш, сделано 2026-11-15** ([ADR 0012](../../adr/0012-tokens-in-memory-and-httponly-cookie.md)):
  - Access-токен клиент держит в памяти (`AccessTokenStore`), в `localStorage` ничего не пишется; остаток старой версии стирается при старте.
  - Новый эндпоинт `POST /auth/refresh` (публичный, по refresh-cookie) отдаёт `accessToken` и пользователя. Refresh-cookie: `HttpOnly`, `SameSite=Strict`, `Path=/rest/auth`, `Secure` вне разработки. `AuthGuard` принимает только Bearer-токен (cookie сама сессией больше не служит, CSRF закрыт). Удалён `ContextInterceptor`, добавлявший `accessToken` в каждый ответ.
  - Клиент: app initializer зовёт `/auth/refresh` при старте; `authRefreshInterceptor` один раз обновляет токен при 401 и повторяет запрос, параллельные запросы делят одно обновление, при неудаче исходная ошибка идёт дальше. Тесты: `auth.service.spec.ts` (клиент), `sessions.test.ts` (сервер).
  - `whoami` и `refresh` отдают поле `id` (раньше приходило `_id`, клиент читал `id`).
- **Ротация refresh-токена с обнаружением кражи, сделано 2026-11-15.** Коллекция `sessions` (одна запись на устройство, TTL-индекс), refresh-токен несёт `sid` и `jti` и меняется при каждом обновлении. Повторное предъявление уже заменённого токена удаляет всю сессию; для двух вкладок, обновляющихся одновременно, прежний токен принимается 10 секунд без новой cookie. `sign-out` теперь завершает сессию только этого устройства (раньше всех), смена пароля по-прежнему отзывает все. Тесты в `sessions.test.ts`: ротация, кража после окна, окно для двух вкладок, чужие устройства, удалённая сессия.
- **Синхронизация вкладок, сделано 2026-11-15.** `BroadcastChannel`: выход в одной вкладке завершает остальные, вход подхватывается из cookie. Тесты в `auth.service.spec.ts`.
- **Не сделано.** CSRF-токен на `/auth/refresh` и `/auth/sign-out` (защищены `SameSite=Strict` и CORS; выход и обновление не меняют данные). Серверная сессия вместо JWT на одном origin с SSR ([S7.5](../E07-vps-hosting/S7.5.md)): пересмотреть там. Абсолютный предел жизни сессии (сейчас скользящая): добавить, если понадобится. Проверка в настоящем браузере: у меня нет браузера, поток проверен тестами сервера (по HTTP) и клиента (HttpTestingController).
