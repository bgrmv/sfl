# S6.10 — Автоматический дамп базы по расписанию

**Эпик:** 6 — Миграция данных и переключение · **Статус:** в [индексе бэклога](../README.md)

**Приоритет:** P2 · **Размер:** S · **Зависит от:** [S6.1](S6.1.md)

**DESC:** Как администратор лиги, я хочу, чтобы сервер сам делал дамп базы при запуске и затем каждые 7 дней, чтобы всегда была свежая копия без ручных действий.

**ACs:**

- [ ] Задача объявлена через `@nestjs/schedule` в отдельном модуле: первый дамп при старте сервера, затем каждые 7 дней. Интервал и каталог назначения задаются конфигурацией (`.env`), а не константами в коде.
- [ ] Дамп делается `mongodump` в архив с меткой времени в имени. Каталог — вне git (`_backups/`, см. «Запреты» в [AGENT.md](../../../AGENT.md)). Архив не содержит секретов в имени и логах.
- [ ] Старые дампы чистятся: хранится настраиваемое число последних (по умолчанию 8).
- [ ] Задача не запускается дважды одновременно; успех и ошибка каждого запуска пишутся в лог, падение дампа не роняет сервер.
- [ ] Включение управляется флагом (`BACKUP_ENABLED`), в тестах и по умолчанию в dev выключено.
- [ ] Юнит-тест на расписание, ротацию и защиту от наложения; восстановление из дампа проверено вручную и описано в `docs/runbooks/mongo-backup.md` ([S6.1](S6.1.md)).

## Заметки

- Это простая локальная часть. Ежедневная выгрузка во внешнее S3-хранилище с шифрованием и алертом остаётся в [S7.8](../E07-vps-hosting/S7.8.md) (P4): она расширяет эту задачу, а не заменяет.
- Общий механизм плановых задач и согласование сценариев — [S10.9](../E10-product-features/S10.9.md) (P4). Если S10.9 будет сделана раньше, этот дамп становится её первой задачей. Зависимость `@nestjs/schedule` добавляется здесь, причина — эта история.
- Нужен `mongodump` в окружении сервера: в dev-container проверить наличие `mongodb-database-tools`, при отсутствии добавить в образ ([docs/development.md](../../development.md), раздел «Rebuild»).
