# S3.27 — Инкрементальный пересчёт статистики и проверочный полный пересчёт

**Эпик:** 3 — Улучшение архитектуры · **Статус:** в [индексе бэклога](../README.md)

**Приоритет:** P2 · **Размер:** L · **Зависит от:** [S3.1](S3.1.md), [S3.5](S3.5.md)

**DESC:** Как администратор лиги, я хочу, чтобы публикация и отзыв матча меняли статистику игроков добавлением и вычитанием вклада этого матча, а не пересчётом всего сезона заново, чтобы сохранение было дешёвым и не упиралось в лимит транзакции MongoDB (60 секунд). Полный пересчёт остаётся как проверочный и восстановительный режим.

**Основание:** разговор 2026-11-16 после S3.5: пересчёт «в лоб» (aggregate по всем матчам сезона на каждого игрока, внутри транзакции) растёт вместе с сезоном. Статистика игрока — свёртка по матчам; свёртка с обратимой операцией считается инкрементально. Kafka и очередь не нужны: лига маленькая, а событие и запись согласуются транзакцией MongoDB ([ADR 0014](../../adr/0014-mongodb-replica-set.md)).

**ACs:**

- [x] Разбор домена записан в ADR: какие поля метаданных игрока и сезона обратимо складываются (суммы, счётчики, результаты), а какие зависят от всего сезона (рейтинги, MVP, серии, максимумы) и потому пересчитываются иначе; выбран подход для каждой группы.
- [x] В `@sfl/domain` есть чистые функции `applyGame(метаданные, матч)` и `revertGame(метаданные, матч)` для обратимых полей (тест сначала): `apply` затем `revert` возвращает исходное значение; порядок применения матчей не меняет результат.
- [x] Свойственный тест: для набора матчей из golden-master инкрементальный результат (матч за матчем) совпадает с полным пересчётом по всем полям, которые объявлены инкрементальными; расхождения не допускаются.
- [x] Сохранение, публикация и отзыв матча в одной короткой транзакции применяют вклад только затронутых матчей игроков; поля, зависящие от всего сезона, помечаются устаревшими или пересчитываются отдельным коротким шагом ([S3.5](S3.5.md) остаётся в силе).
- [x] Полный пересчёт сезона (`POST /players/recalculate/season/full`) и проверка: считает заново на чтении без сессии и сравнивает с хранимым; расхождения возвращает отчётом, запись — по явному флагу; запись одним `bulkWrite` в короткой транзакции.
- [x] Golden-master ([S2.2](../E02-tests-ci/S2.2.md)) не меняется; серверные тесты и `pnpm check` зелёные.

## Заметки

- Отвергнуто: Kafka и внешний брокер (лишняя инфраструктура для ~40 игроков, согласование с Mongo всё равно потребует outbox); outbox с фоновым обработчиком и debounce оставлен как запасной вариант, если часть полей нельзя инкрементировать.
- Заменяет прежний замысел S3.27 «подготовка вне транзакции» (решает ту же проблему иначе).
- Итог: разбор и решение — [ADR 0017](../../adr/0017-incremental-player-statistics.md). Группа (a) (суммы, рейтинги) считается `applyGame`/`revertGame`; списки и серии (группа c) не инкрементируются, а пересобираются для затронутых игроков по лёгкой выборке их учтённых матчей (без полного `aggregate` по сезону); карьера пересчитывается из сезонов. Каждому игроку — одна запись (сезон и карьера вместе).
- Изменение поведения, не значений: при обновлении матча вклад старой версии вычитается у всех, кто в ней был (прежний код пересчитывал только новый состав и оставлял вычеркнутого игрока со старыми числами); `PUT` считает метаданные по новому, а не по прежнему документу (`findOneAndReplace` возвращал старый); `PATCH` считает по сохранённому документу, а не по телу запроса.
- Золотой набор (`test/golden`) не менялся (`golden-baseline.json` тот же), добавлен тест «инкрементальный результат равен пересчёту с нуля» по всем сезонам набора: расхождений нет.
- Осталось: `POST /players/recalculate/season` (пересчёт по списку игроков) пока считает по-старому через `aggregate`; перед включением в проде запустить проверку по каждому сезону (старые метаданные до S3.11/S3.14 могут расходиться, это покажет отчёт).
- Изменение контракта: `POST /players/recalculate/season/full` без `apply` теперь только отчёт, ничего не пишет (раньше пересчитывал и записывал); прежнее действие — `{ seasonId, apply: true }`.
