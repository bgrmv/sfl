# S3.17 — Привести структуру клиента к FSD

**Эпик:** 3 — Улучшение архитектуры · **Статус:** в [индексе бэклога](../README.md)

**Приоритет:** P2 · **Размер:** L · **Зависит от:** [S3.6](S3.6.md)

**DESC:** Как разработчик, я хочу, чтобы слои клиента соответствовали FSD (страницы в `pages`, публичный API у каждого слайса, без кросс-импортов сущностей), чтобы границы можно было проверять линтером ([S3.8](S3.8.md)) и дальше менять UI по частям.

**ACs:**

- [ ] Страницы из `entities/games/pages` и `entities/players/pages` перенесены в `pages/`, виджет `entities/games/widgets` — в `pages/` или `features/` по правилам skill `feature-sliced-design`; маршруты собираются в `app`.
- [ ] `entities/utils` и `entities/charts` перенесены в подходящие места (`shared/lib`, `features`, `pages`); константы правил лиги из `shared/constants` не лежат в `shared`.
- [ ] У каждого слайса `features`, `widgets`, `pages`, `entities` есть `index.ts`; алиасы указывают на слайс; импортов мимо `index.ts` (сейчас 56 в `entities`) нет.
- [ ] Кросс-импорты `games` ↔ `players` ↔ `teams` ↔ `captains` разорваны одной из стратегий skill (слияние границ, вынос общего, сборка в верхнем слое); решение записано в ADR.
- [ ] Файлы названы по домену, а не по роли (`types.ts`, `utils.ts`, `constants.ts`).
- [ ] Слайсы без потребителей (`captain-to-add`, `captains-selection`, `games-table`) удалены или подключены, решение — вместе с [S10.8](../E10-product-features/S10.8.md).
- [ ] `pnpm check` проходит, поведение клиента не изменилось (ручная проверка ключевых страниц).

## Заметки

- Источник: [аудит FSD](../../audits/fsd-client-2026-11-13.md).
- Делать после [S1.4](S1.4.md) (ручная проверка страниц) и до [S3.8](S3.8.md): линтер границ на текущей структуре даст сотни ошибок.
- Не обязательно прийти к «чистому» FSD за один заход: skill допускает минимум слоёв (`app`, `pages`, `shared`) и добавление `entities`/`features` только по необходимости.
