# S3.14 — Пересчёт метаданных всех матчей после исправления расчёта

**Эпик:** 3 — Улучшение архитектуры · **Статус:** в [индексе бэклога](../README.md)

**Приоритет:** P2 · **Размер:** S · **Зависит от:** [S3.11](S3.11.md)

**DESC:** Как администратор лиги, я хочу пересчитать метаданные уже сохранённых матчей и итоги игроков по новым правилам, чтобы старые данные не расходились с исправленным расчётом.

**ACs:**

- [x] `POST /migrations/recalculate-games` (только `ADMIN`) пересчитывает метаданные каждого матча, затем сезонные и карьерные итоги всех игроков, участвовавших в матчах.
- [x] Режим `dryRun=true` ничего не пишет и возвращает, у скольких матчей и игроков значения изменятся.
- [x] Пересчёт идемпотентен: второй запуск ничего не меняет.
- [x] Матч, который не проходит новые правила (нет капитана, нет позиции у опубликованного), не прерывает пересчёт: он попадает в список `skipped` с причиной.
- [x] Тест на синтетической базе: матч, посчитанный по-старому, после запуска получает верные `hasWon` для второй команды, пенальти, очки новой системы.

## Заметки

- Источник: [S3.11](S3.11.md). Метаданные матча хранятся в самом матче (`metadata.players`), поэтому `POST /players/recalculate/season` их не исправляет: он берёт сохранённые значения как есть. Нужен пересчёт самих матчей.
- Запускать до переключения на MVPS ([S6.7](../E06-data-migration/S6.7.md)) и на копии данных, прод не трогать ([AGENT.md](../../../AGENT.md)).
- Старые матчи без позиций у участников нельзя пересчитать как опубликованные: их нужно либо дополнить владельцем, либо перевести в «Черновик»; решение владельца записать здесь.
- **Находка golden-master ([S2.2](../E02-tests-ci/S2.2.md), 2026-11-15):** у всех 16 матчей прода статус `new`, хотя статистика есть. Пересчёт должен сначала перевести сыгранные матчи в `published` (решение владельца, какие именно), иначе итоги игроков обнулятся. Оценка масштаба по обезличенному набору: после исправлений S3.11 метаданные меняются у всех 16 матчей и у 54 из 232 игроков; отчёт — `golden-report.json` рядом с набором.
- Сделано (2026-11-16): `MigrationsService.recalculateGames` и `POST /migrations/recalculate-games`. Тело `{ apply }` (`.strict()`: опечатка ключа или лишний ключ дают 400; пустое тело допустимо). **По умолчанию сухой прогон**, запись только при `apply: true`; query-параметров нет. Матч считается `calculateGameMetadata` и `calculatePlayerGameResultMetadata` из `@sfl/domain`; запись только при отличии хранимых метаданных (сравнение JSON-слепков), поэтому второй запуск ничего не меняет. Метаданные пересчитываются у матчей любого статуса, включая `new`. Запись матчей: пачки по 10, каждая в короткой транзакции. Итоги игроков: `PlayerMetadataService.verifySeason` по каждому сезону (S3.27); в сухом прогоне ему передаются запланированные метаданные (`overrides`), он считает «как будет» и ничего не пишет.
- Отчёт: `applied`, `gamesTotal`, `gamesChanged` (в режиме записи считаются только реально записанные пачки), `playersChanged`, `skipped[{gameId, season, number, reason, message}]`, `failedBatches[{gameIds, error}]`, `seasons[]`. В `skipped` только правила матча: `CAPTAINS_COUNT`, `UNKNOWN_TEAM`, `MISSING_POSITION` (опубликованный матч без позиции у игрока), `INVALID_GAME` (нет массива `statistics`/`teams` и другие `TypeError`). Сорвавшаяся запись пачки идёт в `failedBatches` (текст ошибки без секретов, до 200 символов); если не записалась ни одна пачка, ответ 500. Повторный запуск дозаписывает остаток.
- **Статусы миграция не меняет** ([GLOSSARY.md](../../../GLOSSARY.md), [ADR 0015](../../adr/0015-exclusive-match-editing-lease-in-db.md) п. 5: «Опубликован» выставляет только домен после двух подтверждений). У всех 16 матчей прода статус `new`, а итоги игроков (`verifySeason`, `applyGameChange`) учитывают только `published`. Поэтому после миграции метаданные матчей верны, но итоги игроков по матчам `new` останутся нулевыми/прежними, пока матчи не опубликованы. Публикация 16 матчей прода — отдельное решение владельца через будущий механизм подтверждений ([S10.35](../E10-product-features/S10.35.md)); от него зависят итоги игроков. Матчи без позиций дополняет владелец.
- Итоги сезона пишутся одним `bulkWrite` на сезон (десятки игроков): транзакция короткая.
- Ограничения. Параллельный запуск не защищён: если матчи сезона менялись во время запуска, `verifySeason` повторяет проверку и отвечает 409, а повторный запуск идемпотентен и доведёт дело до конца. Матчи читаются целиком одним запросом; для больших баз нужен курсор. `MISSING_POSITION` проверяется только в миграции, при обычном сохранении матча правило держит DTO. Запись матча не сверяется с его версией, прочитанной в начале (разовая админская операция).
- Золотой набор не менялся (`golden-baseline.json` тот же). Тест на синтетической базе: `server-nest/test/api/migrations.recalculate-games.test.ts`.
