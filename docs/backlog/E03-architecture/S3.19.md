# S3.19 — Типы и контракты API из одной схемы: zod → TypeScript и OpenAPI

**Эпик:** 3 — Улучшение архитектуры · **Статус:** в [индексе бэклога](../README.md)

**Приоритет:** P2 · **Размер:** L · **Зависит от:** [S1.12](../E01-dependency-upgrades/S1.12.md), [S3.4](S3.4.md)

**DESC:** Как разработчик, я хочу описывать каждую форму данных API один раз как схему zod и получать из неё и типы TypeScript, и спецификацию OpenAPI, чтобы клиент, сервер и документация не расходились.

**Идея (владелец, 2026-11-15):** взять конвенции OpenAPI 3.0, переформулировать типы и интерфейсы по доменам (игры, игроки, команды, пользователи, статистика) и вывести их из схем: схема zod — источник, `z.infer` — результирующий тип, OpenAPI генерируется из той же схемы.

**ACs:**

- [ ] Инвентаризация: таблица «домен → схема в `@sfl/schemas` → тип на клиенте → тип/DTO/схема Mongoose на сервере», с дублями и расхождениями. За основу — отчёт knip (≈30 неиспользуемых типов, см. [S11.4](../E11-dx-docs/S11.4.md)).
- [ ] Правила именования и размещения (запись в [docs/PROJECT.md](../../PROJECT.md) и ADR): схема `xSchema`, тип `X = z.infer<typeof xSchema>`; отдельные схемы запроса (create/update) и ответа; домены как папки в `packages/schemas`; без префиксов `I`/`T` и без параллельных `interface`.
- [ ] Каждый домен переведён: клиентские `types.ts` и серверные DTO используют типы из `@sfl/schemas`; дубли удалены. Mongoose-схемы остаются слоем хранения и приводятся к доменным типам явным маппером.
- [ ] OpenAPI 3.0 (или 3.1, выбор — в ADR) генерируется из схем zod (`z.toJSONSchema` в zod 4 или `nestjs-zod`, выбор по ADR) и отдаётся Swagger-ом вместо ручных `@ApiProperty`. Теги, `operationId` и коды ошибок единообразны; формат ошибки `{ statusCode, message, issues }` описан как общая схема ответа.
- [ ] Проверка расхождений в `pnpm check`: сгенерированная спецификация совпадает с закоммиченной (или тест на контракт), сборка падает при расхождении.
- [ ] Нет неиспользуемых экспортов типов в пакетах (проверка knip по `packages/*`, `client/`, `server-nest/` без ложных срабатываний).

## Заметки

- Стартовая точка уже есть: общий пакет `@sfl/schemas` на `zod/mini` ([ADR 0010](../../adr/0010-zod-mini-in-shared-schemas.md)). История расширяет его на все домены и добавляет OpenAPI.
- Направление «zod → OpenAPI», а не «OpenAPI → zod/типы» (кодогенерация клиента): вся кодовая база на TypeScript, схема в коде короче и не требует отдельного шага генерации. Если появится не-TS потребитель API, пересмотреть.
- Новые зависимости (`nestjs-zod`, генератор спецификации) добавляются только после выбора в ADR ([AGENT.md](../../../AGENT.md), «Запреты»).
- Подходящего skill для OpenAPI среди подключённых нет; конвенции берутся из спецификации OpenAPI 3.x и документации zod.
