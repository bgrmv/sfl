# S3.25 — Стор капитанов без дубля списка игроков

**Эпик:** 3 — Улучшение архитектуры · **Статус:** в [индексе бэклога](../README.md)

**Приоритет:** P2 · **Размер:** S · **Зависит от:** [S3.22](S3.22.md), [S3.7](S3.7.md)

**DESC:** Как разработчик, я хочу один источник правды о капитанах, чтобы список игроков и список капитанов не расходились и не загружались двумя запросами.

**Основание:** ревью 2026-11-16: `CaptainsStore` держит свой список (`players/captains`), хотя `PlayersStore` уже содержит тех же игроков и вычисляет `captains`. Рецензент-упроститель оценил выигрыш в около 50 строк; доменный пурист: если у капитанов нет своей проекции, достаточно хранить только выбор (`selected`).

**ACs:**

- [ ] Проверено, нужна ли капитанам отдельная проекция (например, статистика побед из `GET players/captains` отличается от игроков). Если нужна, это `computed` поверх `PlayersStore`, а не второй независимый запрос; решение записано в заметках.
- [ ] `CaptainsStore` хранит только выбор по командам (`selected`) и читает капитанов из одного источника; `toggleCaptain` меняет игрока в одном месте.
- [ ] Тесты на потребителей (`captains-selection`, `captains-table`, `captains-toggle`, `captain-to-add`) написаны до правки.
- [ ] `pnpm check` зелёный.

## Заметки

- Риск средний: затрагивает страницу капитанов и форму матча; без тестов на потребителей не удалять.
