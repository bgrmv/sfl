# S3.21 — Выровнять REST API: лексика, семантика, топология

**Эпик:** 3 — Улучшение архитектуры · **Статус:** в [индексе бэклога](../README.md)

**Приоритет:** P2 · **Размер:** M · **Зависит от:** [S3.20](S3.20.md)

**DESC:** Как разработчик, я хочу, чтобы маршруты, методы, коды ответов и описание Swagger следовали RFC 9110 и OpenAPI, чтобы API был предсказуем и документация говорила правду.

**ACs:**

- [x] Описание без поломки контракта: `DELETE /games/:id` — `200`, `POST /players` — `201`, `PUT /games/:id` описан схемой полной записи, `@ApiParam id` обязателен, `number` — число; у `GET /games/:id` своё описание.
- [x] Теги Swagger во множественном числе (`players`, `users`).
- [x] Пустой `PUT /teams/:id` удалён (молча отвечал `200`).
- [x] `POST /roles` без `@Res()`: ответ проходит через общий интерцептор и получает обёртку `{ ok, data }`.
- [ ] Ответ действий без `{ success: 'OK' }`: создание команды возвращает созданную запись, пересчёт и смена пароля — `204` или `data: null`; клиент и тесты обновлены.
- [ ] Пути: `POST /players/recalculate/season` → ресурс (например, `POST /players/recalculations`); `POST /users/:id/password` → `PUT`; `charts/top-*-players` → один маршрут с параметром системы; клиент обновлён тем же PR.
- [ ] `GET /players/captains` → `GET /players?isCaptain=true` (или оставить с записью причины в ADR).
- [ ] `POST /players` с массивом: объект `{ players: [...] }` или `POST /players/batch`.
- [ ] Решено по `POST /users/test-users` (заглушка) и `GET /users` (какие поля отдаются): убрать или описать.
- [ ] Ошибки и обёртка `{ ok, data }` описаны в OpenAPI; это делает [S3.19](S3.19.md), здесь только сверка.
- [ ] `pnpm check` проходит.
