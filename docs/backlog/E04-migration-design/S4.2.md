# S4.2 — Схема Postgres [если переходим на Postgres]

**Эпик:** 4 — Spike и проектирование переезда · **Статус:** в [индексе бэклога](../README.md)

**Приоритет:** P1 · **Размер:** M · **Зависит от:** [S4.1](../E04-migration-design/S4.1.md), [S4.4](../E04-migration-design/S4.4.md)

**DESC:** Как разработчик, я хочу утверждённую реляционную схему для всех данных лиги, чтобы перенос данных и новый бэкенд опирались на одну модель.

**ACs:**
- [ ] ER-диаграмма и DDL черновик. Предлагаемое соответствие:

  | MongoDB | Postgres |
  |---|---|
  | `users` | `public.users` (email, хеш пароля) + `public.profiles` (имя, фамилия, аватар, возраст). Id пользователей уже UUID, их можно сохранить |
  | `roles`, `users.roles[]` | `public.roles` + `public.user_roles` |
  | `players` | `public.players` (`nickname`, `is_captain`, `status`, `position`, `number`, `user_id` уникальный) |
  | `teams` | `public.teams` (`name` и `color` уникальные, `description`, `logo`) |
  | `games` | `public.games` (`number`, `season`, `played_at`, `status`, `link`, `notes`) |
  | `games.teams[2]` | `public.game_teams` (`game_id`, `team_id`, `side` 1/2, капитан) |
  | `games.statistics[]` | `public.game_player_stats` (голы ногой, головой, с пенальти, автоголы, пасы, MVP, трансфер, капитан, позиция) |
  | `players.metadata`, `games.metadata` | Вычисляемые: представления или кеш-таблицы, пересчитываются из `game_player_stats` |
- [ ] Для `ObjectId` выбрано правило: новые UUID и колонка `legacy_id` для обратной связи.
- [ ] Перечислены enum-ы (`player_status`, `player_position`, `game_status`, `team_color`, `role`), ограничения, индексы и внешние ключи.
- [ ] Решено, хранить ли `metadata` кешем (jsonb или таблицы) или считать на лету. Решение подтверждено замерами на объёме прод-данных.
- [ ] Схема согласована с командой и записана в ADR.

## Заметки

⛔ Отменена 2026-10-25: база остаётся MongoDB (сначала Atlas, затем в compose на MVPS — [S6.9](../E06-data-migration/S6.9.md)), переход на Postgres не планируется.
