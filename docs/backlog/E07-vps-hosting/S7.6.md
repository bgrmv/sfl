# S7.6 — Деплой из GitHub Actions

**Эпик:** 7 — Хостинг на VPS · **Статус:** в [индексе бэклога](../README.md)

**Приоритет:** P2 · **Размер:** S · **Зависит от:** [S7.2](../E07-vps-hosting/S7.2.md), [S2.1](../E02-tests-ci/S2.1.md)

**DESC:** Как разработчик, я хочу, чтобы слияние в `main` само выкатывало staging, а прод выкатывался одной кнопкой, чтобы не заходить на сервер для деплоя.

**ACs:**
- [ ] Workflow собирает образ после зелёного CI и публикует его в GHCR с тегами `sha-<commit>` и `main`.
- [ ] Деплой на staging запускается автоматически: по ssh в `/opt/sfl/staging/` обновляются compose-файл и `deploy/caddy/sfl.caddy`, затем выполняется `docker compose pull && docker compose up -d`. Если файл маршрутов изменился, выполняются `caddy validate` и `caddy reload` в edge-прокси ([S7.9](../E07-vps-hosting/S7.9.md)).
- [ ] Деплой затрагивает только папку `/opt/sfl/<окружение>/` и не перезапускает чужие контейнеры.
- [ ] Деплой в прод — ручной шаг через GitHub Environment с подтверждением. Выкатывается тот же образ, что прошёл staging.
- [ ] Откат — повторный деплой предыдущего тега. Команда описана в runbook.
- [ ] Ssh-ключ деплоя отдельный, с правами только на deploy-пользователя, хранится в GitHub Secrets.
- [ ] После деплоя workflow проверяет `GET /rest/health` и главную страницу. При ошибке деплой помечается упавшим.
