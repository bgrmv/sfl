# SFL — устройство проекта и обязанности

Живой документ для быстрого входа в проект и выравнивания людей и агентов. Если что-то из описанного ниже перестало быть правдой, исправь документ в том же PR. Правила для агентов и команды проверок — в [AGENT.md](../AGENT.md), статусы работ — в [бэклоге](backlog/README.md), детали архитектуры — в [blueprint](Project_Architecture_Blueprint.md).

Статусы: **есть** — уже в репозитории, **цель** — принятое решение, ещё не реализовано (путь к нему в бэклоге).

## 1. Что это

SFL — приложение для любительской футбольной лиги: матчи, игроки, капитаны, статистика и рейтинги. Angular SPA + NestJS API + MongoDB. Целевая схема: монолит Nest + Angular SSR на VPS (S4.1).

Язык лиги и правила расчёта (матч, трансфер, MVP, системы счёта) записаны в [GLOSSARY.md](../GLOSSARY.md); это источник истины для тестов и кода расчёта.

## 3. Методологии

### 3.1 FSD (Feature-Sliced Design) — клиент

Слои `client/src`: `app` → `pages` → `features` → `entities` → `shared`. Импорт только вниз по списку; соседние срезы одного слоя друг друга не импортируют (исключение — `@x` между сущностями, [ADR 0016](adr/0016-client-fsd-layers-and-cross-imports.md)). Слайс импортируется только через `index.ts`, это проверяет ESLint. Слой `widgets` не используем: блок одной страницы лежит в `pages/<страница>/ui`.

| Слой       | Ответственность                                               |
| ---------- | ------------------------------------------------------------- |
| `app`      | запуск, роутинг, провайдеры, глобальные стили                 |
| `pages`    | экраны-маршруты, только сборка из нижних слоёв                |
| `features` | действия пользователя (вход, выбор капитанов, создание матча) |
| `entities` | бизнес-сущности (игрок, матч, капитан): модель, API, UI       |
| `shared`   | переиспользуемое без бизнес-смысла: UI-кит, утилиты, конфиг   |

Внутри среза: `ui/`, `model/` (signal store), `api/`, публичный `index.ts` — снаружи импортируют только через него.

### 3.2 CQRS — разделение команд и запросов

- **Команда** меняет состояние и ничего не возвращает, кроме id/результата операции. **Запрос** читает и ничего не меняет.
- Сервер (цель): модуль на сущность, внутри `commands/`, `queries/`, обработчики отдельными классами; контроллер только принимает DTO и отправляет команду или запрос в шину. Расчёт статистики — запросы; запись матчей и игроков — команды. Авторизацию и валидацию (zod) делают на границе, до обработчика.
- Клиент: чтение и запись в сторах `@ngrx/signals` разделены — методы-запросы (`load*`, computed) и методы-команды (`create*`, `update*`, `delete*`) не смешиваются.
- Единая БД (read/write модели не разносим), event sourcing не используем. Пока `@nestjs/cqrs` не добавлен в зависимости, разделение держим на уровне структуры файлов и именования; решение о библиотеке — отдельной историей ([эпик 3](backlog/E03-architecture/)).

### 3.3 DDD и порядок разработки (тесты, домен, локальное)

Всегда в таком порядке ([ADR 0013](adr/0013-tests-first-then-domain-then-local.md)): **1) тест**, **2) домен**, **3) локальные вещи**. Правила лиги (очки, системы счёта, MVP, статусы матча, подтверждения, рейтинги, награды) пишутся чистым TypeScript в `packages/domain` без Angular, Nest и Mongoose; сервер и клиент считают одними функциями. Сторы, контроллеры, репозитории, компоненты и стили — тонкие адаптеры вокруг домена. Контексты: Матч, Рейтинг, Люди, Сообщество; язык кода — термины [GLOSSARY.md](../GLOSSARY.md).

### 3.4 Оформление клиента

Тема на Angular Material (M3) со своими токенами `--sfl-*`: **основная тёмная**, светлая добавляется в самом конце ([S10.50](backlog/E10-product-features/S10.50.md)), поэтому до неё `color-scheme: dark` и переключателя темы нет; компоненты UI-кита лежат в `shared/ui`, стили компонента изолированы (`ViewEncapsulation.Emulated`, без `::ng-deep`), глобальные только токены и сброс; SCSS: токены, миксины, типографика отдельными файлами. Состояние страницы, которым делятся ссылкой (сезон, система счёта, участники сравнения), живёт в адресе. Обзор и оценка: [implementation-assessment.md](design/implementation-assessment.md).

## 5. Обязанности и правила

**Каждый участник (человек или агент):**

1. Работает по истории бэклога; статус меняет только в индексе бэклога.
2. Перед коммитом запускает `pnpm check` из корня — он должен проходить.
3. Не коммитит секреты, `.env`, дампы, бэкапы; не трогает прод; не коммитит и не пушит без просьбы владельца.
4. Пишет коммиты как `feat|fix|chore|docs(область): ... (S<id>)`, на английском.
5. Держит документацию в актуальном состоянии: изменились стек, структура, команды или методология — правит этот файл и [AGENT.md](../AGENT.md).

**Код:**

- Клиент: signals вместо RxJS там, где это возможно; слои FSD не нарушаем; новые компоненты standalone.
- Сервер: валидация на границе, с учётом перехода на zod; чтение и запись разделены (CQRS).
- Комментарии — только если причина неочевидна.
- Новая логика идёт с тестами (Vitest); расчёт статистики защищён golden-master тестами (S2.2).

### 5.1 Права доступа API

Два глобальных guard'а ([auth.guard.ts](../server-nest/src/shared/guards/auth.guard.ts), [roles.guard.ts](../server-nest/src/shared/guards/roles.guard.ts)) работают по принципу «закрыто по умолчанию»: новый маршрут без декораторов доступен только роли `ADMIN`.

| Доступ         | Как задаётся              | Маршруты                                                                                                                                                                |
| -------------- | ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Без токена     | `@Public()`               | `POST /auth/sign-in`, `POST /auth/sign-out`, `GET /games`, `GET /games/:id`, `GET /players`, `GET /players/:id`, `GET /players/captains`, `GET /teams`, `GET /charts/*` |
| Любой вошедший | `@Roles()` без аргументов | `GET /auth/whoami`                                                                                                                                                      |
| Только `ADMIN` | по умолчанию              | всё остальное: изменения матчей, игроков, команд, ролей, `GET /users`, `POST /users/:id/password`, `POST /migrations/*`, `POST /players/recalculate/season`             |

Публичные маршруты игроков отдают без токена только имя и аватар; полного пользователя (email, фамилия, возраст, id) получает `ADMIN` на тех же маршрутах, если приложен токен (`presentPlayer`, [S8.10](backlog/E08-security-privacy/S8.10.md)). Графики никогда не отдают email и фамилию.

Без токена изменяющий маршрут отвечает 401, с токеном без нужной роли — 403. Роли в access-токене действуют до 15 минут после смены; при входе по refresh-cookie пользователь и роли читаются из базы, поэтому смена роли действует сразу. Refresh-токен меняется при каждом обновлении, повторное использование старого удаляет сессию; выход завершает сессию устройства, смена пароля отзывает сессии всех устройств (`tokenVersion`); токены несут только `_id`, `roles`, `tv`, `iss`, `aud`. Access-токен клиент держит в памяти, refresh лежит в HttpOnly-cookie с `Path=/rest/auth` и открывает только `POST /auth/refresh` и `POST /auth/sign-out`; остальные маршруты принимают лишь Bearer ([ADR 0012](adr/0012-tokens-in-memory-and-httponly-cookie.md)) ([S8.12](backlog/E08-security-privacy/S8.12.md)). `PATCH /players/:id` меняет только поля из белого списка (`UpdatePlayerDTO`), пользователя берёт из игрока, а не из тела; пароль меняется только через `POST /users/:id/password`. Матрица «роль × маршрут» проверяется в `server-nest/test/api/access.test.ts`, и тест полноты не даёт добавить закрытый маршрут без строки в ней.

Вход защищён от перебора ([S8.11](backlog/E08-security-privacy/S8.11.md)): не больше 5 попыток в минуту по IP и по e-mail на `POST /auth/sign-in` и мягкий общий лимит 300 запросов в минуту по IP; превышение даёт `429` с `Retry-After`. Лимиты задаются окружением (`SIGN_IN_LIMIT`, `API_LIMIT` и др.). Заголовки безопасности ставит `helmet` (HSTS и CSP — прокси), Swagger доступен только вне production.

### 5.2 Ответы и ошибки API

Каждый ответ — `Result<T, ApiError>` ([ADR 0011](adr/0011-result-response-format.md)): успех `{ ok: true, data }`, ошибка `{ ok: false, error: { status, code, message, issues? } }`. Статус HTTP осмысленный (2xx или 4xx/5xx). `code` — стабильная строка (`NOT_FOUND`, `VALIDATION_FAILED`, `UNAUTHORIZED`, ...), клиент ветвится по ней; `issues: [{ path, message }]` только у валидации. Типы и `Ok`/`Err` — в `@sfl/schemas`. Ответ формируют [глобальный перехватчик](../server-nest/src/shared/interceptors/response.interceptor.ts) и [фильтр](../server-nest/src/shared/filters/all-exceptions.filter.ts); контроллеры возвращают обычные значения и не используют `@Res()` (для cookie — `@Res({ passthrough: true })`).

Правила для кода: исключения Nest бросаются **экземплярами** (`throw new NotFoundException(...)`), сервисы не глотают ошибки и не возвращают `null` вместо исключения, неожиданная ошибка уходит наружу как обычный 500 без внутренностей. На клиенте `HttpService` отдаёт сервисам `data`, а оператор `toResult()` превращает вызов в `ApiResult<T>` для экранов, которые реагируют на ошибку.
