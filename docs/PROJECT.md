Живой документ для быстрого входа в проект и выравнивания людей и агентов. Если что-то из описанного ниже перестало быть правдой, исправь документ в том же PR. ## 1. Что это

SFL — приложение для любительской футбольной лиги: матчи, игроки, капитаны, статистика и рейтинги. Angular SPA + NestJS API + MongoDB. Целевая схема: монолит Nest + Angular SSR на VPS (S4.1).

## 3. Методологии

### 3.1 FSD (Feature-Sliced Design) — клиент

Слои `client/src`: `app` → `pages` → `widgets` → `features` → `entities` → `shared`. Импорт только вниз по списку; соседние срезы одного слоя друг друга не импортируют.

| Слой | Ответственность |
|---|---|
| `app` | запуск, роутинг, провайдеры, глобальные стили |
| `pages` | экраны-маршруты, только сборка из нижних слоёв |
| `widgets` | самостоятельные блоки экрана из нескольких features/entities |
| `features` | действия пользователя (вход, выбор капитанов, создание матча) |
| `entities` | бизнес-сущности (игрок, матч, капитан): модель, API, UI |
| `shared` | переиспользуемое без бизнес-смысла: UI-кит, утилиты, конфиг |

Внутри среза: `ui/`, `model/` (signal store), `api/`, публичный `index.ts` — снаружи импортируют только через него.

### 3.2 CQRS — разделение команд и запросов

- **Команда** меняет состояние и ничего не возвращает, кроме id/результата операции. **Запрос** читает и ничего не меняет.
- Сервер (цель): модуль на сущность, внутри `commands/`, `queries/`, обработчики отдельными классами; контроллер только принимает DTO и отправляет команду или запрос в шину. Расчёт статистики — запросы; запись матчей и игроков — команды. Авторизацию и валидацию (zod) делают на границе, до обработчика.
- Клиент: чтение и запись в сторах `@ngrx/signals` разделены — методы-запросы (`load*`, computed) и методы-команды (`create*`, `update*`, `delete*`) не смешиваются.
- Единая БД (read/write модели не разносим), event sourcing не используем. Пока `@nestjs/cqrs` не добавлен в зависимости, разделение держим на уровне структуры файлов и именования; решение о библиотеке — отдельной историей ([эпик 3](backlog/E03-architecture/)).

## 5. Обязанности и правила

**Каждый участник (человек или агент):**
1. Работает по истории бэклога; статус меняет только в индексе бэклога.
2. Перед коммитом запускает `pnpm check` из корня — он должен проходить.
3. Не коммитит секреты, `.env`, дампы, бэкапы; не трогает прод; не коммитит и не пушит без просьбы владельца.
4. Пишет коммиты как `feat|fix|chore|docs(область): ... (S<id>)`, на английском.
5. Держит документацию в актуальном состоянии: изменились стек, структура, команды или методология — правит этот файл и [AGENT.md](../AGENT.md).

**Код:**
- Клиент: signals вместо RxJS там, где это возможно; слои FSD не нарушаем; новые компоненты standalone.
- Сервер: валидация на границе, с учётом перехода на zod; чтение и запись разделены (CQRS).
- Комментарии — только если причина неочевидна.
- Новая логика идёт с тестами (Vitest); расчёт статистики защищён golden-master тестами (S2.2).

### 5.1 Права доступа API

Два глобальных guard'а ([auth.guard.ts](../server-nest/src/shared/guards/auth.guard.ts), [roles.guard.ts](../server-nest/src/shared/guards/roles.guard.ts)) работают по принципу «закрыто по умолчанию»: новый маршрут без декораторов доступен только роли `ADMIN`.

| Доступ | Как задаётся | Маршруты |
|---|---|---|
| Без токена | `@Public()` | `POST /auth/sign-in`, `POST /auth/sign-out`, `GET /games`, `GET /games/:id`, `GET /players`, `GET /players/:id`, `GET /players/captains`, `GET /teams`, `GET /charts/*` |
| Любой вошедший | `@Roles()` без аргументов | `GET /auth/whoami` |
| Только `ADMIN` | по умолчанию | всё остальное: изменения матчей, игроков, команд, ролей, `GET /users`, `POST /users/:id/password`, `POST /migrations/*`, `POST /players/recalculate/season` |

Публичные маршруты игроков отдают без токена только имя и аватар; полного пользователя (email, фамилия, возраст, id) получает `ADMIN` на тех же маршрутах, если приложен токен (`presentPlayer`, [S8.10](backlog/E08-security-privacy/S8.10.md)). Графики никогда не отдают email и фамилию.

Без токена изменяющий маршрут отвечает 401, с токеном без нужной роли — 403. Роли берутся из токена (до 15 минут после смены, проверка по базе — [S8.12](backlog/E08-security-privacy/S8.12.md)). `PATCH /players/:id` меняет только поля из белого списка (`UpdatePlayerDTO`), пользователя берёт из игрока, а не из тела; пароль меняется только через `POST /users/:id/password`. Матрица «роль × маршрут» проверяется в `server-nest/test/api/access.test.ts`, и тест полноты не даёт добавить закрытый маршрут без строки в ней.

### 5.2 Ошибки API

Все ошибки приходят в одном виде: `{ statusCode, message, error? }`, у валидации ещё `issues: [{ path, message }]`. Это делает [глобальный фильтр](../server-nest/src/shared/filters/all-exceptions.filter.ts). Правила для кода: исключения Nest бросаются **экземплярами** (`throw new NotFoundException(...)`), сервисы не глотают ошибки и не возвращают `null` вместо исключения, неожиданная ошибка уходит наружу как обычный 500 без внутренностей.
