История: [S12.2](../backlog/E12-performance/S12.2.md). Аудит только читает: код не менялся, индексы не создавались, прод-Atlas не трогали.

## 1. Резюме

- **Проверено:** все запросы `server-nest` (игры, игроки, команды, пользователи, графики, пересчёт статистики), объявленные индексы и индексы в локальной базе, `explain("executionStats")` основных запросов, размер ответов и время на локальной копии прода.
- **Условия:** `pnpm check` перед аудитом проходит (17 шагов). Локальная база `sfl` на replica set `rs0` ([S3.23](../backlog/E03-architecture/S3.23.md)): 16 игр (сезоны 2024 и 2025), 232 игрока, 235 пользователя, 2 команды, 2 роли, 4 сессии. Прод заметно больше (лига играет с 1980 года, около 2 400 игр при полном вводе), поэтому находки считаются на рост.
- **Итого:** 6 находок: 0 высоких, 2 средних, 4 низких. Все запросы на сегодняшних данных быстрее 60 мс (измерено через HTTP на `node dist/main.js`).
- **Главный вывод:** индексы для основных запросов есть и используются. Риск — не медленные запросы, а объём: `GET /games` без сезона отдаёт каждую игру целиком (18 КБ на игру), публично и без лимита. Второе: мелкие пробелы в индексах (`statistics.playerId`), одинокие индексы без потребителей и пустая запись сезона после удаления матча.

## 5. Находки

### Группа А. Объём ответа

**А1. `GET /games` без сезона отдаёт все матчи целиком.** Средняя. Проверено.
`games.controller.ts:35-62`, `games.service.ts:68`: `find({ ...game })` без лимита и без проекции, маршрут публичный. Документ матча: 12,5 КБ в базе (из них 8 КБ метаданных, 20 строк статистики), 18 КБ на проводе. Сейчас 16 игр = 293 КБ; при 2 400 играх (1980–2026 целиком) ≈ 43 МБ за один запрос от любого посетителя. Клиент зовёт с `season` (`games.store.ts:94`), страница матча с `season` и `number`, но сервер не запрещает вызов без параметров.
Воспроизведение: `GET /rest/games` против `GET /rest/games?season=2024`, 293 КБ против 40 КБ.
→ [S12.4](../backlog/E12-performance/S12.4.md) (лимит и проекция без статистики для списка); пагинация — [S10.1](../backlog/E10-product-features/S10.1.md).

### Группа Б. Индексы

**Б1. Нет индекса на `games.statistics.playerId`.** Средняя на рост, низкая сейчас. Проверено `explain`.
`players.service.ts:158`: `exists({ 'statistics.playerId': id })` при удалении игрока — `COLLSCAN` по играм (16 из 16 сегодня; при 2 400 играх читает до 30 МБ документов). Многоключевой индекс по `statistics.playerId` закрывает и этот запрос, и `distinct('statistics.playerId', { season })` в пересчёте.
→ S12.4.

**Б2. Индексы без потребителей.** Низкая. Проверено чтением кода.
`games.number` (одиночный) полностью покрыт составным `{number, season}` с `number` первым; `players.nickname` не используется ни одним запросом (поиск по нику на клиенте). Лишний индекс замедляет запись и занимает память. `games.season` нужен (запросы по сезону, составной индекс начинается с `number`).
→ S12.4 (убрать `number` и `nickname` или записать, зачем они).

**Б3. Фильтры по `metadata.bySeason.<сезон>…` читают всех игроков.** Низкая, «не чиним сейчас». Проверено `explain`.
`charts.service.ts` (`$match` по `metadata.bySeason.N.ancientRatingSystem.totalPoints`) и `findSeasonPlayerIds` (`$exists`): `COLLSCAN` 232 документа за 3 мс. Индекс по динамическому пути на каждый сезон — это до 47 индексов; при росте до 1 000 игроков скан остаётся единицами миллисекунд. Пересмотреть при ~5 000 игроках или p95 графиков > 100 мс.
→ «не чиним» (причина выше).

### Группа В. Пересчёт статистики

**В1. На каждый сохранённый матч до 3 запросов на каждого игрока, по очереди.** Низкая. Гипотеза по чтению кода, время не измерено.
`player-metadata.service.ts:100-175`: на каждого из ~20 затронутых игроков последовательно `findById`, `find` игр сезона (`applyToSeason`), `updateOne`: порядка 60 запросов в транзакции на одно сохранение. Внутри транзакции параллельность невозможна, но можно заменить чтение игроков одним `find({_id: {$in}})` и записи одним `bulkWrite` (так уже сделан `apply` полного пересчёта, строка 366). Полный пересчёт сезона ради одного матча не запускается: подтверждено, что `applyGameChange` трогает только игроков матча и только его сезон.
→ S12.4 пунктом «если измерение покажет заметное время»; сначала замер на реальной записи матча.

**В2. После удаления матча в `players.metadata.bySeason` остаётся пустая запись сезона.** Низкая. Проверено чтением.
`player-metadata.service.ts:~232`: `if (!counted.size) return freshSeason()` — пустая запись `bySeason[сезон]` пишется (`$set` на строке 162 всегда), и фильтр `$exists` в `findSeasonPlayerIds` её находит; полный пересчёт поэтому считает игрока «с метаданными сезона».
→ S12.4 (удалять запись сезона через `$unset`, если игр нет); поведение API не меняется, это пункт AC истории.

### Группа Г. Отсутствует

Медленных запросов на сегодняшних данных нет: максимум 56 мс на `GET /players`.
