# Аудит проекта SFL

Аудит ничего не чинит: только читает, проверяет и описывает. Исправления оформляются историями бэклога.

## Границы

- Исходники, конфиги и зависимости не менять. Писать можно только в `docs/audits/`.
- Папки `_backups/`, `_dumps/`, `ssl/` и файлы `.env` не читать. В отчёт не попадают секреты, email и данные из локальной копии прода.
- Базу трогать только на чтение и только локальную (`mongodb://mongodb:27017`).
- `pnpm check` перед аудитом должен проходить; результат запиши в начало отчёта.

## Порядок

1. Прочитай историю аудита и `docs/PROJECT.md` (стек, FSD, CQRS).
2. Разбери `server-nest` и `client` по отдельности, затем стык между ними (контракты API, DTO).
3. Каждую находку проверь: воспроизведи (тест, запрос к локальному серверу) или подтверди чтением кода. Непроверенное помечай «гипотеза».
4. Сгруппируй находки по причине, а не по файлам.
5. Для группы заведи историю по правилу 6 из `docs/backlog/README.md` или пометь «не чиним» с причиной.

## Формат отчёта `docs/audits/<тип>-YYYY-MM-DD.md`

1. **Резюме** — 5–10 строк: что проверено, сколько находок по серьёзности, главный вывод.
2. **Карта доменных областей** — игроки, матчи, команды, капитаны, пользователи, статистика: кто кого вызывает, где циклы и пересечения ответственности. Таблица «область → модуль сервера → срез клиента → зависит от».
3. **Находки по группам.** Для каждой: `файл:строка`, что не так, воспроизведение (вход и ожидаемый результат), серьёзность, статус (проверено / гипотеза).
4. **Истории** — таблица «группа → история или "не чиним"».
5. **Что не проверено** и почему.

## Серьёзность

- Высокая: потеря или порча данных, обход авторизации, утечка персональных данных, падение сервера.
- Средняя: неверный результат расчёта, 500 вместо 4xx, нарушение границ слоёв, дублирование расчёта.
- Низкая: мёртвый код, нейминг, стиль.
